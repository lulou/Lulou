BUG 2 — Wrong first-call card after cancellation/decline

Current incorrect behaviour:

- A call starts.
- The caller ends the call before it is answered, or the recipient declines.
- The receiving user returns to the chat.
- The “You’ve both shared a lot / Start First Call” card appears immediately.
- In some cases the user is told they declined even though the caller cancelled.

The backend must be the authority for the final reason.

Distinguish these outcomes:

- recipient_declined
- caller_cancelled
- missed
- timed_out
- ended_after_connection
- connection_lost

Rules:

- If the caller ends before answer:
 Recipient sees:
 “{callerName} cancelled the call.”

- If the recipient explicitly presses Decline:
 Caller sees:
 “Call declined.”

- If nobody answers before timeout:
 Both users see:
 “Missed call.”

- If the call connected and later ended:
 Both users see:
 “Call ended.”

- Never show “You declined the call” unless that exact user pressed Decline.

Investigate:

1. The caller End button mutation.
2. The recipient Decline mutation.
3. The server cancel/decline/end endpoints.
4. WebRTC or realtime signals:
  call:declined
  call:cancelled
  call:ended
  call:timeout
5. Cache updates for:
  ["/api/matches"]
  ["/api/matches", matchId]
6. messaging.tsx call-card rendering condition.
7. Whether callStage, messagesRemaining, callStartedAt, callSessionId, callAnswered and callCompleted are enough to distinguish the final reason.
8. Whether a stale ring signal can restore the old call state after cancellation.

Requirements:

- Use the real callSessionId throughout the entire lifecycle.
- Reject stale signals from old sessions.
- Only one terminal state may win.
- Patch and invalidate both list and detail caches.
- Do not use arbitrary 4-second suppression timers.
- Do not show the “Start First Call” card while:
 - a call is ringing
 - a call is active
 - the latest session is still being finalised
 - a cancellation/decline status message should be shown
- After the correct terminal status has rendered, the user may start a new call again.
