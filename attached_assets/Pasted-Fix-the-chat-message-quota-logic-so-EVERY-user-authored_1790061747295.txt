Fix the chat message quota logic so EVERY user-authored message counts toward the sender’s remaining message allowance, including voice notes.

Current bug:

- Text messages correctly deduct from the sender’s remaining message count.
- Voice notes do NOT deduct from the sender’s remaining message count.
- This means users can effectively bypass the stage message quota by sending voice notes.

That must be fixed.

==================================================
EXPECTED RULE
==================================================

For message-stage quotas, EVERY outbound user message should count as ONE message unless it is explicitly a system message.

That includes:

- normal text message = -1
- voice note = -1

Example:

User has 5 messages remaining.

They send:

voice note
voice note
voice note

Remaining count must become:

2

If they then send one text message:

remaining count becomes:

1

==================================================
1. USE ONE AUTHORITATIVE MESSAGE-COUNT RULE
==================================================

Do NOT maintain separate quota counting logic for text and voice notes.

Create/use one authoritative helper for whether a message consumes quota.

Something equivalent to:

isQuotaConsumingUserMessage(message)

should return TRUE for:

- text message from user
- voice note from user

and FALSE for:

- system messages
- call-history messages
- stage notifications
- automated Lulou messages
- other non-user-authored system events

Use existing message types/schema where possible.

==================================================
2. VOICE NOTES MUST NOT BYPASS THE STAGE
==================================================

A user must not be able to send unlimited voice notes while text quota remains fixed.

Example:

Stage allows 12 messages.

User sends:

6 text
6 voice notes

That user has used all 12 messages.

They should not be able to send another user-authored message until the next progression state permits it.

==================================================
3. COUNT PER SENDER
==================================================

Preserve the existing rule that quotas are tracked independently for each participant.

If:

User A has 5 remaining
User B has 9 remaining

A sending a voice note:

A → 4
B remains 9

Do not alter the other user’s outgoing allowance.

==================================================
4. DEDUCT ONLY AFTER SUCCESSFUL MESSAGE CREATION
==================================================

Do not consume quota simply because recording started.

A voice note should count when the authoritative voice-note message is successfully created/sent.

Do NOT deduct for:

- cancelled recording
- failed recording
- failed upload
- failed transcode
- message insert failure

If send ultimately succeeds:

deduct exactly ONE.

==================================================
5. RETRIES MUST NOT DOUBLE-DEDUCT
==================================================

Voice-note uploads already use a stable clientRequestId / message ID.

Use that same idempotency principle for quota counting.

If a failed request is retried:

do NOT deduct another message if the same authoritative message already exists.

One successful voice-note message = exactly one quota unit.

==================================================
6. REALTIME UI UPDATE
==================================================

As soon as a voice note successfully sends:

the sender’s remaining message count should update immediately.

Do not wait for:

- polling
- leaving/re-entering chat
- page refresh

Example:

display says:

5 messages left

voice note successfully sends

immediately display:

4 messages left

Then reconcile with authoritative server state.

==================================================
7. RECIPIENT/STAGE SYNC
==================================================

Because message counts affect stage progression, the other user must also receive the updated authoritative stage/message state through the existing realtime system.

If a voice note causes a user to reach their message quota:

the counterpart should see that progression state immediately.

No stale:

“2 messages remaining”

after those messages were actually voice notes.

==================================================

==================================================

Find why voice notes are currently excluded.

Check for logic such as:

- counting only messages with text
- ignoring `__VOICE__:` messages
- filtering attachment/media messages
- only counting message_type === "text"
- SQL counts excluding voice-note type
- frontend count calculation different from backend
- stage resolver using old text-only logic

Fix the ROOT counting rule, not just the visible number.

==================================================
9. SERVER MUST BE AUTHORITATIVE
==================================================

Do not rely only on frontend decrement.

The backend/stage resolver must count voice notes as quota-consuming messages too.

Otherwise refresh/device-switch will restore the wrong count.

Server truth must be:

text + voice notes = user-authored message count

according to the current stage window.

Audit whether already-sent voice notes inside the CURRENT active stage should be included when recomputing remaining messages.

Use existing stage boundaries/timestamps/message ranges correctly.

- “Missed call from…”
- “First call complete”
- Lulou stage messages
- availability events
- other automated/system rows

Only genuine messages authored/sent by the user should consume message allowance.

MESSAGE QUOTA CONSUMPTION
