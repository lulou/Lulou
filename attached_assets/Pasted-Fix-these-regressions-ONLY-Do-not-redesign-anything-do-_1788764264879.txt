INCOMING CALL TRIGGERING WHEN APP LOADS
Bug:
An incoming call/ringing state appeared immediately when loading the app even though no genuine incoming call was happening.

Fix:

Incoming call UI and ringtone must ONLY trigger from a genuinely active incoming call session intended for that user.
On app startup, clear any stale local call state, stale ringing state, stale persisted call session data, stale timers, and stale WebRTC state.
Do not restore an old incoming call from localStorage/sessionStorage/cache unless the backend confirms that call is still genuinely active.
Realtime call events must be validated against:

correct receiver user ID
active call status
current valid call/session ID
call not already ended, declined, cancelled, timed out, or answered
Old realtime events must never retrigger ringing after reopening the app.
Ensure duplicate subscriptions/listeners are cleaned up properly.
Only one active incoming-call event should be handled at a time.
Failed, ended, declined, cancelled, expired, or stale calls must immediately reset the full call state.
Expected result:
Opening or refreshing Lulou never randomly causes ringing. Incoming call UI only appears when another real user is actively calling that account.

INTENTION WHEEL ALLOWS MORE THAN ONE SPIN
Bug:
The Intention Wheel allowed the same user to spin multiple times even though its eligibility rules already exist.

Restore the existing intended rules exactly:

If user receives at least 10 eligible likes in a day:
User gets ONE Intention Wheel spin for that daily eligibility period.
Otherwise:
User gets ONE free spin per week.
A user must never be able to repeatedly spin by:

refreshing
reopening the app
navigating away and back
double tapping
sending repeated API requests
using multiple tabs/devices
frontend state resetting
This MUST be enforced server-side/database-side, not only by disabling the button.

Requirements:

Check eligibility before allowing a spin.
Record the spin atomically.
Prevent race conditions and duplicate spins.
Add/verify appropriate unique constraints or transaction locking if required.
The spin endpoint must reject a second spin when no new eligibility exists.
Frontend must immediately update to the locked/used state after a successful spin.
Reopening the app must load the true eligibility state from the backend.
Do not reset the weekly or daily window incorrectly because of timezone/client clock differences.
Use the backend as the source of truth.
Do not change the current Intention Wheel design, animation, Open/Close flow, DNA logic, colours, or profile presentation.

Expected result:
Each user receives exactly the number of spins they are entitled to and cannot bypass the restriction.
