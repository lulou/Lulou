Root reason the webhook path is unreliable: STRIPE_WEBHOOK_SECRET env var is UNSET. The getWebhookSecret() function falls back to a DB query:

// stripeClient.ts:231–240
const isLive = (process.env.STRIPE_SECRET_KEY ?? '').startsWith('sk_live');
const row = await pool.query(
  `SELECT secret FROM stripe._managed_webhooks WHERE livemode = $1 ...`,
  [isLive]
);

This adds a DB round-trip to every webhook. If that query is slow on the first delivery, constructEvent hasn't run yet when Stripe gives up (it retries, but the first delivery may time out).

The one gap: webhook is never being received
The entire purchase completed correctly via the activate-fallback path. Nothing is broken for the user today. However, the webhook path has two structural issues:

Issue A — STRIPE_WEBHOOK_SECRET not set as an env var

Every webhook request hits the DB to read the secret, adding latency before constructEvent can run. Set this in Replit Secrets:

STRIPE_WEBHOOK_SECRET = whsec_Ns6KEGYcHnIxSpzw7aKlsi1r2Vya4Ziz

Issue B — Webhook URL is the ephemeral dev domain

https://86d5f2d5-2c53-4a30-af8a-399676f90be0-00-1pwwt7ymw85zn.spock.replit.dev

This URL changes every time the Repl restarts. When the backend moves to a stable URL (Replit deployment, Railway, etc.), the Stripe webhook endpoint must be updated to match. Until then, the activate-fallback on the success page is the reliable grant path — and it is working correctly.
