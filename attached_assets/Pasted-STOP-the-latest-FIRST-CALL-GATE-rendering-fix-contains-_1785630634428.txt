STOP: the latest FIRST_CALL_GATE rendering fix contains a progression-breaking mistake.

The affected database state is:

- call_stage = 0
- message_count_1 = 15
- message_count_2 = 0

Lulou requires 15 messages EACH WAY before the first call stage unlocks.

Therefore this match has NOT reached FIRST_CALL_GATE as a whole.

The newly added logic is incorrect:

partnerAtLimit = partner message count >= quota

effectiveIsLimitReached =
 isLimitReached ||
 partnerAtLimit ||

This can unlock the call gate for both users as soon as only one person sends 15 messages.

Remove that behaviour.

Do not deploy or retain any logic where either user reaching the quota unlocks the call stage.

CORRECT PROGRESSION RULE

For Stage 1:

user1Complete = message_count_1 >= 15
user2Complete = message_count_2 >= 15

firstCallGateUnlocked =
 user1Complete && user2Complete

The call stage unlocks only when BOTH are true.

Correct UI before both are complete:

User who has completed their 15:
- cannot send additional messages
- sees:
 “You’ve completed your messages”
 “Waiting for [name] to finish”
- sees the other user’s remaining count
- must not see Continue, availability or Start Call
- cannot create a call session

User who has not completed their 15:
- normal composer remains available
- sees their real remaining count
- continues messaging until they reach zero
- must not see the call-stage gate yet

Once both users reach 15:
- hide both message composers
- show “Call stage unlocked”
- show Continue and End Match
- then follow the availability flow
- only show Start Call after both users complete the required availability step
