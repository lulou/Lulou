CORRECT COUNTDOWN RULE

The header represents how many messages the currently signed-in user can still SEND during the current messaging stage.

Stage limits:

- Stage 1: 15 sent messages per user
- Stage 2: 12 sent messages per user
- Stage 3: 20 sent messages per user

Formula:

messagesLeft = max(0, currentStageLimit - mySentMessageCountForCurrentStage)

Examples for Stage 1:

- before sending: 15 left
- after first successful message: 14 left
- after second: 13 left
- after fifteenth: 0 left

The partner sending a message must not reduce my allowance.

REQUIRED SERVER BEHAVIOUR

When a message is accepted:

1. Insert the message.
2. Increment only the authenticated sender’s count.
3. Perform both operations atomically in one database transaction.
4. Enforce the current stage limit server-side.
5. Return the canonical updated values:

- message
- sender message count
- current stage
- current stage limit
- messages left

Do not increment the recipient’s count.

Do not increment when:

- message insertion fails
- request is duplicated
- sender has already reached the limit
- match is at a call gate
- message is rejected

Prevent duplicate requests from consuming two message allowances.

REQUIRED CLIENT BEHAVIOUR

After a successful send:

- immediately reduce the sender’s displayed countdown by one
- patch the exact match-detail cache used by the header
- use the canonical count returned by the server
- invalidate/refetch the match detail afterward for confirmation
- keep the optimistic message and counter consistent
- roll both back if the send fails

Do not wait for a page refresh.

When a realtime message arrives from the partner:

- add the incoming message
- do not reduce my countdown
- update the partner’s count in shared match data if needed
- do not overwrite my current count with stale data
