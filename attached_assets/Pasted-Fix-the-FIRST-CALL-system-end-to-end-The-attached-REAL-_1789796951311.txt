Fix the FIRST CALL system end-to-end. The attached REAL screenshots prove the current production flow is still too slow and not functioning like a real phone call.

There are TWO critical problems:

1. Availability takes far too long to synchronize between the two users.
2. Clicking Start First Call does not create a proper live call experience.

This needs to be fixed as one realtime call system, not as separate UI patches.

==================================================
1. AVAILABILITY MUST SYNC INSTANTLY
==================================================

Current production problem:

One user selects:

Available now

but the other user can wait around ONE MINUTE before Lulou recognizes it and finally shows:

Start First Call

That is unacceptable.

Expected behavior:

User A selects Available now
→ server saves immediately
→ User B receives realtime event immediately
→ User B UI updates immediately
→ if both users are compatible, Start First Call appears immediately

Target perceived latency:
well under 1 second after the realtime event reaches the other client.

Do NOT make the user wait for:

- slow polling
- a periodic refetch
- page refresh
- tab switch
- reopening chat

Realtime must be the primary path.

==================================================

- polling interval
- staleTime
- cacheTime

- realtime listener mounted only on one page
- availability event not subscribed globally
- database update succeeds but other client does not receive event
- service worker caching
- server response delay
- stale local state
- timezone mismatch
- availability compatibility computed only after a refetch timer

Do not guess.

availability_click

→ database commit
→ realtime event emitted
→ realtime event received
