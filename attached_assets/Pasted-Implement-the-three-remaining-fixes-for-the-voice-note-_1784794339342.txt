Implement the three remaining fixes for the voice-note engagement unlock.

Do not change any unrelated feature.

CURRENT STATE

Commit b8b94ae already implements:
- Voice notes unlock when both users reach 10 eligible messages each
- Voice notes are free
- First call remains at 15 messages each
- Server-side enforcement exists
- Payment requirements were removed

Only fix the three PARTIAL requirements below.

1. SERVER-PERSISTED POPUP-SEEN STATE

The popup-seen state is currently stored only in localStorage.

Replace this with server-persisted state stored separately for each user and each match.

Add a table such as:

voice_note_popup_seen
- match_id
- user_id
- seen_at

Use a composite primary key or unique constraint on:
(match_id, user_id)

Requirements:

- Each user must see the unlock popup once.
- User A dismissing it must not mark it seen for User B.
- The state must survive:
 - refresh
 - logout/login
 - switching browsers
 - switching devices
 - clearing localStorage
- The server must verify that the authenticated user belongs to the match.
- Keep localStorage only as an optional UI cache, not the source of truth.

Add endpoints or extend the entitlement response so the client receives:

{
 unlocked: boolean,
 popupSeen: boolean
}

Add an authenticated endpoint to mark the popup as seen.

The Continue button must call that endpoint successfully before permanently dismissing the popup.

Prevent duplicate rows using an idempotent insert or upsert.

2. TRUE REALTIME UNLOCK

The current implementation polls every 10 seconds.

Replace the unlock delay with a realtime update.

When the second user reaches 10 messages and the voice_note_unlocks row is created:

- Broadcast a realtime event for that match
- Both connected clients must receive the event
- Immediately invalidate or update the entitlement query
- Immediately enable the microphone
- Immediately show the popup for each user whose popupSeen state is false

Use the existing Supabase Realtime system or the app’s existing match-channel infrastructure.

Requirements:

- No page refresh
- No 10-second wait
- No duplicate popups
- No duplicate unlock rows
- Handle simultaneous messages safely
- Retain a low-frequency fallback refetch only if needed for reconnect recovery, not as the primary unlock mechanism
- Unsubscribe cleanly when leaving the conversation

3. RETROACTIVE UNLOCK FOR EXISTING MATCHES

Existing matches may already have progressed beyond the first call and had their message counters reset.

Fix this so they are not incorrectly shown as locked.

When checking entitlement:

Grant voice-note access when either:

A. A voice_note_unlocks row already exists

OR

B. Both current message counters are at least 10

OR

C. The match history proves the match already progressed beyond the original first-call threshold

Use a reliable existing progression indicator such as:
- call_stage > 0
- completed first-call record
- stage history
- another existing persisted progression field

Do not rely only on reset message counters.

When condition B or C is true:
- Insert voice_note_unlocks with on-conflict-do-nothing
- Return unlocked: true

Also add a safe backfill during startup or migration for existing matches already beyond the first-call stage.

The backfill must:
- Be idempotent
- Not reset message counts
- Not modify call progress
- Not create duplicate rows
- Not unlock matches that never reached the required stage

- Voice-note sending must remain server-enforced.
- Do not expose other users’ private state.
- Do not weaken any existing auth middleware.
