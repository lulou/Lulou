The backend must fail safely:

- return a clear 400 response for legacy values
- do not crash
- do not clear existing availability
- do not partially update one field and then fail
- client should refetch and ask the user to choose availability again

Confirm the set-availability update and agreed_call_at calculation happen atomically in one database operation or transaction.

CALL-SCHEDULE COUNTDOWN

Verify the CALL_SCHEDULED screen updates while it remains open.

It must not calculate “Available in X minutes” only once during render.

Required:

- update the displayed countdown at least every 30–60 seconds
- automatically transition from CALL_SCHEDULED to READY_TO_CALL when the 5-minute early-start window begins
- no manual refresh required
- clear the interval on unmount or match change
- use server-derived agreed_call_at as the source of truth

SERVER-TIME SAFETY

Do not trust the phone’s clock for authorising call start.

- client time may only control the displayed countdown
- the server must use its own current time for Gate 3b
- if the client believes the call is ready but the server says it is early, show the server error and refetch the match
- do not create a call session when rejected

AVAILABILITY UPDATE RACE

Test both users selecting or changing availability at nearly the same time.

The final agreed_call_at must be calculated from the latest two persisted timestamps.

Avoid this race:

1. Read partner availability.
2. Another request changes it.
3. Write agreed_call_at using the stale value.

Use a transaction, row lock or atomic database calculation so the match cannot retain an agreement based on outdated availability.

CHANGING AVAILABILITY

When either user changes their selection:

- update only their timestamp
- recompute agreed_call_at immediately
- broadcast the new state to both users
- if the new choices mismatch, remove the old agreement
- if the call was scheduled, the previous scheduled time must no longer remain active
- do not alter message counts or call_stage

EXPIRED AVAILABILITY

Define behaviour when agreed_call_at is significantly in the past.

Suggested rule:

- allow the call during a reasonable grace window, such as 30 minutes after agreed_call_at
- after the grace window, show “Availability expired — choose another time”
- clear or invalidate agreed_call_at
- require both users to confirm availability again
- do not leave Start Call permanently available hours or days later

Implement the final agreed grace-window rule server-side and use the same rule for the client display.
